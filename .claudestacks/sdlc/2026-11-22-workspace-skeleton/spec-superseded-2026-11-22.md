# Spec: Workspace skeleton

This spec delivers the empty Cargo workspace every later herdrify milestone builds on:
- the nine crates and the downward-only dependency edges of ADR 0001
- shared package metadata, dependencies and lints, inherited by every member
- a pinned toolchain
- a one-command Definition-of-Done gate, a supply-chain check, and CI that runs both

It implements no herdrify behaviour. The single executable line prints the command's name and
version (§4.2).

All paths under `evidence/` are relative to this chain directory. `evidence/probe-workspace/` is a
throwaway copy of the exact workspace this spec describes. Every gate run cited below was made on
it.

## 1. Premises

**Tool versions.**
- Inside the workspace, the pinned toolchain is rustc 1.94.1 / cargo 1.94.1.
- The other tools are rustup 1.29.3, cargo-make 0.37.24 and cargo-deny 0.20.2.

(`evidence/tool-versions.txt`.)

**Rust version floor.** `rust-version = "1.94"` is airsl 0.1.4's floor. `cargo info airsl@0.1.4`
prints `rust-version: 1.94` (`evidence/airsl-rust-version.txt`).

**ADRs relied on.**
- ADR 0001: the crate list, layers, and downward-only normal dependency edges.
- ADR 0002: the SDKs declare no Cargo features and depend on no herdrify crate.
- ADR 0007: `herdrify-cli` uses `herdrify-testkit` at runtime for `herdrify test`, so the CLI
  depends on testkit normally.

**Crate names are free.** None of the nine crate names, nor `herdrify`, exists on crates.io:
`cargo info <name>` exits 101 with "could not find". The control, `cargo info airsl`, exits 0
(`evidence/crates-io-names.txt`).

## 2. Architecture

This section was approved by the author on its own before this spec was written.

```
 herdrify/
 ├─ Cargo.toml  Cargo.lock  rust-toolchain.toml  Makefile.toml  deny.toml
 ├─ .github/workflows/ci.yml
 └─ crates/
    ├─ herdrify-core     lib            (no deps)
    ├─ herdrify-hc       lib            (no deps)
    ├─ herdrify-app      lib            (no deps)
    ├─ herdrify-lua      lib  → core
    ├─ herdrify-herdr    lib  → core, hc, app
    ├─ herdrify-store    lib  → core
    ├─ herdrify-git      lib  → core
    ├─ herdrify-testkit  lib  → core
    └─ herdrify-cli      bin `herdrify` → core, lua, herdr, store, git, testkit
```

| Unit | Why it exists | How it is tested |
|---|---|---|
| each `lib.rs` | crate root; export-only, carrying only a `//!` block (§4.1) | It holds no logic, so the export-only exemption applies (`unit-test-mandate.md:19`). |
| `herdrify-cli/src/main.rs` | the binary | A colocated `#[cfg(test)]` test of `version_line` (`unit-test-mandate.md:9-13`). |
| the workspace as a whole | the groundwork of ADR 0001 | The gate (§5), `cargo deny check` (§6) and CI (§7). |

**Dependency direction.** Normal dependencies point only downward. The three bottom crates have
none (§4).

**Guideline rules applied** (`claudestacks-guideline-rust` 0.1.5, `skills/rust-guidelines/`):

| Rule | Source | Applied as |
|---|---|---|
| Workspace layout | `references/workspace.md` | members under `crates/`, the root has no `[package]`, `[workspace.*]` is centralised, members inherit with `*.workspace = true`, `path` in `[workspace.dependencies]` is root-relative, version plus path for publishing, one committed `Cargo.lock` |
| Lint table | `references/strict-quality.md:23-27` | its notable entries (§3) |
| Crate roots | `references/mod-rs-export-only.md:7-30` | export-only, with the four-question `//!` block (§4.1) |
| Unit tests | `references/unit-test-mandate.md:9-25` | the binary's logic is tested, and the exemption line is near the top of each `lib.rs` (§4.1) |
| Doc text | `references/doc-comment-discipline.md:14-19,89` | no ADR, milestone or plan references in crate docs or crate READMEs |
| One responsibility | `references/modularity.md` Rule 1 | one responsibility per crate |
| The gate | `SKILL.md:16-22` | the five Definition-of-Done commands (§5) |

Some references govern nothing in this change:
- `static-dispatch.md` and `strong-types.md`: no traits and no public items exist yet.
- `microsoft-guidelines.md`, `M-MIMALLOC-APP` (a binary sets a global allocator): it would add an
  external dependency, which §11 excludes, to a binary that does no work.

### 4.1 Library crate roots

Each library's `src/lib.rs` contains only a `//!` block (`mod-rs-export-only.md:7-21`):
- the first line says what the crate is
- the exemption line comes next, near the top (`unit-test-mandate.md:25`), worded plainly and
  never as a rule number (`doc-comment-discipline.md:14`)
- then the four-question answers: why the crate exists, its responsibilities, and its
  non-responsibilities (`mod-rs-export-only.md:23-30`)

The block describes the crate's role. It makes no claim that any item exists. The exact text of
each library root is the same path under `evidence/probe-workspace/crates/`. `herdrify-core`'s, for
example:

```rust
//! Domain types, ports and use cases of herdrify, with no I/O.
//!
//! This crate root holds no logic, so it carries no unit tests.
//!
//! herdrify's rules live here so they can be tested without Herdr, a filesystem, a network or a Lua
//! engine. The crate performs no I/O and depends on no async runtime, Lua engine or Herdr client.
//!
//! Responsibilities:
//!
//! - domain types: components, bundles, grants, the lock
//! - the traits through which herdrify reaches outside systems
//! - the use cases that combine them
//!
//! Non-responsibilities:
//!
//! - talking to Herdr, the filesystem, git or Lua; adapter crates do that
```

### 4.2 The binary

**Why not an empty `main`?** A plain `fn main() {}` fails the gate: clippy's nursery lint
`missing_const_for_fn` reports "this could be a `const fn`" in the bin test build, and the command
exits 101 (`evidence/probe-main-plain.txt`). The alternatives the probe tried
(`evidence/probe-main-variants.txt`):

| Case | Variant | Result |
|---|---|---|
| A | `const fn main() {}` | passes; prints nothing |
| B | `fn main() -> ExitCode` | fails the same lint |
| C | `#[expect]` on `fn main() {}` | fails as an unfulfilled expectation in the non-test build |
| D | printing the version | passes |

**Why D.** The author chose D over A. It gives a visible smoke check that the binary builds and
runs, at the cost of one line of behaviour, which the intent's "no behaviour" non-goal otherwise
excludes. `version_line` builds the line, and a colocated test covers it.

`crates/herdrify-cli/src/main.rs`:

```rust
//! The `herdrify` command.
//!
//! Prints the command's name and version on standard output and exits.

fn main() {
    println!("{}", version_line());
}

/// The line the command prints: its name and its package version.
fn version_line() -> String {
    format!("herdrify {}", env!("CARGO_PKG_VERSION"))
}

#[cfg(test)]
mod tests {
    use super::version_line;

    #[test]
    fn version_line_names_the_command_and_its_package_version() {
        assert_eq!(
            version_line(),
            format!("herdrify {}", env!("CARGO_PKG_VERSION"))
        );
    }
}
```

`cargo run -q -p herdrify-cli` prints `herdrify 0.0.0` and exits 0 (`evidence/probe-run.txt`).

## 5. The gate

`Makefile.toml` at the root defines three tasks:
- `dod`, also the `default` task: runs the five Definition-of-Done commands in order:
  fmt-check, clippy, doc (with `RUSTDOCFLAGS="-D warnings"`), test, test-doc
- `fmt`, the only task that rewrites files
- `deny`, which is not part of `dod`

`min_version` is the cargo-make version the gate was proven with.

```toml
[config]
default_to_workspace = false
skip_core_tasks = true
min_version = "0.37.24"

[env]
CARGO_TERM_COLOR = "always"

[tasks.default]
alias = "dod"

[tasks.dod]
category = "Gate"
description = "Definition of Done: every step exits 0 with zero warnings"
dependencies = ["fmt-check", "clippy", "doc", "test", "test-doc"]

[tasks.fmt-check]
category = "Gate"
command = "cargo"
args = ["fmt", "--all", "--", "--check"]

[tasks.clippy]
category = "Gate"
command = "cargo"
args = ["clippy", "--workspace", "--all-targets", "--all-features", "--", "-D", "warnings"]

[tasks.doc]
category = "Gate"
command = "cargo"
args = ["doc", "--workspace", "--all-features", "--no-deps"]

[tasks.doc.env]
RUSTDOCFLAGS = "-D warnings"

[tasks.test]
category = "Gate"
command = "cargo"
args = ["test", "--workspace", "--all-targets", "--all-features"]

[tasks.test-doc]
category = "Gate"
command = "cargo"
args = ["test", "--workspace", "--all-features", "--doc"]

[tasks.fmt]
category = "Format"
command = "cargo"
args = ["fmt", "--all"]

[tasks.deny]
category = "Supply chain"
command = "cargo"
args = ["deny", "check"]
```

On the probe workspace, `cargo make dod` runs exactly those five commands
(`evidence/probe-gate-full.txt:7,8,19,39,105`) and exits 0 (`:156`). The full unfiltered log has
no `warning` or `error` lines (`grep -c -E '^(warning|error)'` gives 0). The gate passes with every
inter-crate edge declared and unused, so this lint table raises no unused-dependency warning.

## 7. CI

`.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

env:
  CARGO_TERM_COLOR: always
  CARGO_INCREMENTAL: 0
  CARGO_NET_RETRY: 10
  RUSTUP_MAX_RETRIES: 10
  RUST_BACKTRACE: 1

jobs:
  dod:
    name: Definition of Done
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    timeout-minutes: 45
    steps:
      - uses: actions/checkout@v5

      - name: Install the pinned Rust toolchain
        shell: bash
        run: |
          rustup toolchain install
          cargo --version
          cargo clippy --version
          cargo fmt --version

      - name: Cache cargo registry and target dir
        uses: Swatinem/rust-cache@v2
        with:
          shared-key: gate-${{ matrix.os }}

      - name: Install cargo-make
        uses: taiki-e/install-action@v2
        with:
          tool: cargo-make@0.37.24

      - name: cargo make dod
        run: cargo make dod

  deny:
    name: Supply chain
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v5

      - name: Install the pinned Rust toolchain
        run: rustup toolchain install

      - name: Install cargo-deny
        uses: taiki-e/install-action@v2
        with:
          tool: cargo-deny@0.20.2

      - name: cargo deny check
        run: cargo deny check
```

**Triggers.** CI runs on pushes to `main`, on every pull request, and on manual dispatch. The
author chose this reading of the intent's "on every push and pull request": a feature branch gets
CI once its pull request is open.

**It parses.** On cargo 1.94.1 with yaml-rust2 0.10.4, the file has exactly that structure
(`evidence/probe-ci-yaml.txt`):
- the three triggers, with `push` limited to `main`
- `contents: read`
- a `dod` job over `ubuntu-latest`, `macos-latest` and `windows-latest`
- a `deny` job on `ubuntu-latest`

**What it shares with airsl's passing CI.** Compared with airsl's workflow at commit 1a926b3, the
`dod` job differs in four lines, and the `deny` job in two (`evidence/ci-vs-airsl-diff.txt`):

| Change | Why |
|---|---|
| `rustup show` → `rustup toolchain install` | rustup 1.29.3 documents `toolchain install` as installing "by default the active toolchain", while `show` only shows toolchains (`evidence/probe-rustup-install.txt`). In this workspace it resolves the toolchain from `rust-toolchain.toml` and exits 0 (same file). |
| tools pinned to `cargo-make@0.37.24` and `cargo-deny@0.20.2` | The install action documents the `@version` syntax (`evidence/taiki-install-action-v2-README.md:44-51`), and supports both tools on Linux, macOS and Windows (`evidence/taiki-install-action-v2-TOOLS.md:30,39`). These are the versions the gate was proven with. |
| airsl's Developer Mode step and `cargo make examples` dropped | Both serve airsl alone: its symlink tests and its examples. |

**The shared blocks work on all three runners.** airsl run 44676722443 built commit 1a926b3 on a
push to `main`. All three of its Definition of Done jobs and its Supply chain job succeeded
(`evidence/airsl-ci-jobs.txt`). That run used `actions/checkout@v5`, `Swatinem/rust-cache@v2` and
`taiki-e/install-action@v2` on every runner, and each runner reported cargo 1.94.1, clippy 0.1.94
and rustfmt 1.8.0 for a `channel = "1.94"` pin (`evidence/airsl-ci-run-44676722443-excerpts.txt`).

**No formatting config.** airsl has no `.gitattributes`, `rustfmt.toml` or `.rustfmt.toml`
(`evidence/airsl-format-config-absent.txt`, with a control), and its Windows `dod` job, which runs
`cargo fmt --check`, passed. herdrify adds none either.

**Not proven yet.** That this exact file passes on GitHub cannot be shown before it is pushed. The
first pull request's run is the acceptance check (§10).

## 9. Edge cases and errors

The skeleton takes no input and defines no refusals or error messages of its own. Every failure is
the tools' own output.

| Case | What happens | Proof |
|---|---|---|
| A directory under `crates/` without a `Cargo.toml` | Every cargo command fails, starting `error: failed to load manifest for workspace member …/crates/<dir>` and naming `crates/*`, with exit 101. The fix is to remove the directory. | `evidence/probe-stray-dir.txt` |
| A stray file under `crates/` (e.g. `.DS_Store`) | Harmless; exit 0. | `evidence/probe-stray-dir.txt` |
| Nested Cargo workspaces under `.claudestacks/` (four probe roots, each with its own `[workspace]`) | They are not members. `cargo metadata` lists exactly the nine crates; `cargo make dod` and `cargo deny check` exit 0. | `evidence/probe-nested-workspaces.txt` |
| An empty `main` | Fails clippy, so `main` prints the version instead (§4.2). | `evidence/probe-main-plain.txt` |
| Unused inter-crate dependencies | No warning; the gate passes. | §5 |
| A dependency under a licence outside `allow` | `cargo deny check` fails, exit 4, until `deny.toml` allows it. | `evidence/probe-deny-license.txt` |
| A member published before its dependencies | `cargo package` fails for that member. | `evidence/probe-package.txt` |
| Pinned toolchain or tools missing locally | `CLAUDE.md` lists `rustup toolchain install` and the pinned `cargo install`. CI installs both itself. | §7, §8 |
| A newer cargo-make or cargo-deny | Not covered. The gate is proven on the pinned versions only, and CI and `CLAUDE.md` install exactly those. | §1 |
| Windows line endings | No `.gitattributes` or rustfmt config is added. | §7 |

## 10. Acceptance

The skeleton is done when all of the following hold:
1. On a clean checkout with no `target/`, `cargo make dod` exits 0 with no `warning` or `error`
   lines.
2. `cargo deny check` exits 0.
3. `cargo run -q -p herdrify-cli` prints `herdrify 0.0.0`.
4. `cargo tree -e normal -p <crate> --depth 1` gives exactly the edges in §4 for every member.
5. Every file §3–§7 names equals the same path under `evidence/probe-workspace/`.
6. `CLAUDE.md` and `README.md` read as §8 says.
7. The CI workflow's three `dod` legs and its `deny` job succeed on the branch's first pull
   request.

## 11. Non-goals

- Any herdrify behaviour beyond the version line (§4.2): no ports, SDK clients, Lua, Herdr files or
  argument parsing.
- External dependencies. airsl, tokio and their build needs arrive with the milestones that use
  them.
- The `herdrify-core` → `herdrify-testkit` dev-dependency. It arrives with the first core test.
- Publishing or reserving crate names, release automation, changelogs and version bumps.
- A `.gitattributes`, `rustfmt.toml` or `clippy.toml`.
